# AviUtl2 の公開制御経路の再調査（2026-09-18）

## 結論

本日再取得した公式 SDK でも、プロジェクト全体の保存・読み戻し、Undo 実行、バッチ登録・開始を要求する公開関数は見つからなかった。これは調査対象内での **未発見** であり、全手段で実現不可能という判定ではない。標準 UI の保存・読込み・バッチ操作は公式に説明されているが、それらを外部アプリから呼ぶ自動化契約までは確認できない。仕様・ADR・製品実装は変更していない。

## 操作別の公開範囲

以下の行番号は公式 SDK の対応ファイル（CP932 復号後）を指す。[SDK 一次資料](https://spring-fragrance.mints.ne.jp/aviutl/aviutl2_sdk.zip)

|要求|確認した入口|判定と限界|
|---|---|---|
|全体保存・読込み|`register_project_save_handler` / `register_project_load_handler`（plugin2.h 941–947）|保存直前・読込み直後の通知登録。開始要求や保存成功通知ではない。開始 API は未発見|
|全体退避・復元|`PROJECT_FILE`（856–892）|文字列・バイナリはプラグインごとの領域。全プロジェクトのシリアライズ・復元 API ではない|
|Undo|`call_edit_section`（682–693）|更新ロック内で操作し、編集オブジェクトを一括 Undo 登録する。Undo を実行する公開入口は未発見|
|シーンも含む Undo|シーン設定関数（354–374）|シーン操作は Undo 非対応と明記。ここは未発見ではなく、明記された制約|
|バッチ登録・開始|HOST_APP_TABLE と EDIT_HANDLE、公式サンプル|開始関数は未発見。メニュー登録は独自機能を追加する API で、標準メニューを起動する API ではない|
|出力状態の観測|`get_edit_state`（728–732）|ファイル出力中を観測できる。処理 ID、成功・失敗、バッチ全体の完了通知ではない|
|出力プラグインの終了|`OUTPUT_PLUGIN_TABLE::func_output`（output2.h 99–101）、`func_is_abort`（66–68）|自分の出力処理と中止要求を扱える。全バッチ終了やホストの編集復帰完了とは別|
|出力設定の保持|`FLAG_PROJECT_CONFIG` と `func_load_project_config` / `func_save_project_config`（output2.h 93–119）|プロジェクト側に出力設定を保持する公開入口がある。検証用識別子・設定の受け渡し候補。全体保存の呼出しではない|
|標準 UI の制御|`get_host_app_window`（725–726）|HWND の取得だけで、既存コマンドの ID や実行契約は規定されていない|

`WindowClient.cpp`（85–105、110–153）の `WM_COMMAND` は自分で作ったボタンを処理して SDK に編集を依頼するもの。標準保存・Undo の非公開コマンドを呼ぶサンプルではない。`restart_host_app`（702–703）は存在するが、指定した退避プロジェクトを排他下で復元する保証は記載されていない。[SDK 一次資料](https://spring-fragrance.mints.ne.jp/aviutl/aviutl2_sdk.zip)

`AviSaver.cpp` は中止要求でフレームループを抜けた後にも `true` を返す（119–138）。したがってサンプルの戻り値だけを流用して「全フレーム完成」と判定しない。自作出力では中止、処理数、ファイル確定を別に記録する必要がある、という実装上の推論になる。[SDK 一次資料](https://spring-fragrance.mints.ne.jp/aviutl/aviutl2_sdk.zip)

本体説明の 694–702 行は、出力ダイアログのバッチ登録と、ファイルメニューのバッチ出力画面からの開始を説明する。1296 行にはバッチ終了時の開始前プロジェクト復帰がある。ただし任意の編集失敗に対する復元 API とは書かれていない。705 行以降のコマンドライン説明は **インストーラ用** で、編集本体の出力 CLI と取り違えない。調査範囲にバッチの CLI / RPC / COM 制御仕様は見つからなかった。[公式本体同梱説明](https://spring-fragrance.mints.ne.jp/aviutl/aviutl2_v2.1.9.zip)

## 次に試せる範囲と停止条件

1. **公開 SDK で進められる限定検証**：専用出力プラグインの `FLAG_PROJECT_CONFIG` を使い、登録時の識別子と出力設定がバッチ実行時に復元されるか、別設定のバッチを順に実行して確認する。開始・中止・処理フレーム数を自前記録する。ただし UI による登録が必要なままなら、保存→登録の排他ゲートの完了には数えない。
2. **標準 UI を使う方式は未検証の候補**：保存・読込み・バッチ開始という実在する操作を利用できるが、排他下での呼出し、ダイアログ処理、第三者操作との競合を独立に検証する必要がある。UI の手動成功を製品からの自動制御成功へ一般化しない。
3. **一般的な自動復元の新しい SDK 入口は得られていない**：同じ alias 再生成・手動 Undo の反復はしない。公にサポートされた入口の提供・確認、または標準 UI 自動制御を採用候補として扱う判断が必要。非公開 WM_COMMAND 番号の推測や内部メモリ操作は行っていない。

今回の調査だけでは、排他中の全体自動復元も、保存から出力までの連続した自動保護も合格に変更できない。[既存実機検証と残件](editor-transaction-validation.md)を維持する。
