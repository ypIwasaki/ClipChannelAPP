## 2. アプリの目的・利用環境・機能範囲

### 2.1 目的と利用者

動画のダウンロード、文字起こし、切り抜き作成、字幕・表現の編集、動画の書き出しを一つのアプリから扱う。最終的な用途は、YouTubeで活動する配信者の切り抜き動画・ショート動画の作成である。後続版ではアップロードやチャンネル運用に必要な機能も扱う。

利用者・配布範囲は自分だけとし、通常は1人で利用する。別PCでの作業に備え、初回版からDBの引き継ぎを可能にする。

### 2.2 利用環境

| 項目 | 仕様・状態 |
| --- | --- |
| ホスト端末 | Windowsデスクトップ |
| アプリの形態 | デスクトップアプリ |
| 開発・検討対象の環境 | WSLを使用する。文字起こしの実行候補はWSL内のLinux環境 |
| WSLの構成 | WSL1／2、ディストリビューション・版、導入状態は未確認。WSL2・GPU・Dockerを自動的に必須にしない |

| 外部編集ソフト | AviUtl2を優先する。WSL利用を理由にLinux内のAviUtl2実行や互換レイヤーの採用を決定しない |

## 3. 利用フローと処理間の入出力

### 3.1 工程の関係

利用者はアプリを起動し、工程とその対象を選んで実行する。保存済みの情報・素材を使用できるため、毎回ダウンロードから始める必要はない。

```text
URLと取得設定 → 素材のDL → 必要なMP4変換 → 保存・素材確認
                                                    ↓
                                       文字起こし（本文・開始・終了）
                                                    ↓
                                       利用者による内容・時刻の修正
                                           ┌────────┴────────┐
                                     採用した集計・解析     発話・非発話区間の切り出し
                                                           ↓
                                                利用者によるクリップ選択
                                                           ↓
                                                字幕・表現などの編集
                                                           ↓
                                                動画と編集プロジェクトの保存
```

矢印は情報の関係を示す。各工程を自動起動する指示ではない。通常の動画取得で必要なMP4化を行うことと、文字起こし・解析・編集まで自動連続実行することを区別する。

### 3.2 工程の入力・出力

| 工程 | 利用する入力 | 次の工程・利用者へ渡すもの |
| --- | --- | --- |
| 取得 | URL・利用者の取得設定 | 取得した動画、元URL等の情報、実際の保存先、処理結果 |
| MP4化 | 正常に取得した動画、採用した変換条件 | MP4、保持した変換前動画、それぞれの関係・保存先、処理結果 |
| 文字起こし | 元動画の音声に対応する入力、採用したモデル・設定 | 本文、区間開始・終了時刻、元動画との対応、別実行としての結果 |
| 確認修正 | 利用者が開いた文字起こし結果 | 自動保存が完了した本文・時刻。未保存内容とは区別 |
| 集計・解析 | 利用者が選んだ文字起こし結果に含まれる情報、採用した規則 | 頻出語等の採用範囲の結果、元動画との対応、別実行結果 |
| トリミング | 元動画1件、使用する文字起こし結果、区間の定義、前後余白 | 発話・非発話それぞれのクリップ、元動画・時刻との関係 |
| 編集 | 同一元動画の選択クリップ、文字・時刻・配置・効果等の編集指定 | 編集後の状態、動画ファイル、編集プロジェクト、処理・復元結果 |
| 圧縮・展開 | 保存済みファイルまたは圧縮ファイル、利用者の明示指示 | 可逆的な圧縮物または復元したファイル。処理元も保持 |
| DB引き継ぎ | 保存済みDB情報、書き出し・取り込みの指示 | 対応関係を保った引き継ぎ用データ、取り込み後の保存情報 |

上表は必要な情報の意味を示す。JSONの項目名、通信方式、SQLのテーブル、関数シグネチャ、特定のID形式を定義したものではない。

### 3.3 アプリとツールの責務

本アプリは対象指定、保存・関連付け、結果の選択、処理の所有管理、必要な確認、データ保護、状態表示を担う。外部ツールは、対応する入力を受け取り、取得・認識・変換・編集などを担う。ツールの終了コードだけで、アプリ側の登録・保存・品質まで一括して成功とはしない。

Windows側の編集連携、WSL側の処理、保存制御、ログ加工をどう分割するかは設計上の候補であり、別サービス・別リポジトリ・特定のGUI基盤の採用は未確定である。

## 4. 機能仕様

### 4.1 F-01：素材のDL・MP4化・再利用

| ID | 項目 | 動作仕様 |
| --- | --- | --- |
| DL-01 | 取得対象 | 使用するyt-dlpで取得可能な動画を対象とする。YouTubeだけに限定せず、本アプリ独自の取得対象の制限を設けない。すべてのURLの成功を保証する意味ではない |
| DL-02 | 通常入力 | 利用者が動画URLを1件と取得設定を指定し、取得を実行する |
| DL-03 | 設定範囲 | 利用するyt-dlpの全CLIオプション・操作機能をGUIから利用できること。一部の主要設定だけへの縮小はしない |
| DL-04 | 取得結果 | 保存した動画と、元URL・元動画ID・タイトル・作成日等の基本情報を管理する。動画の実体と情報を別に保持する |
| DL-05 | MP4保存 | 元動画はMP4で保存する。取得物がMP4以外なら変換し、拡張子だけの変更で代替しない |
| DL-06 | 取得物がMP4の場合 | MP4という形式要件だけを理由に再変換を必須にしない。再生互換性・映像音声の符号化条件は未確定 |
| DL-07 | 変換前動画の保持 | MP4変換が成功しても、変換前の取得済み動画を変換後のMP4とともに残す。不要な場合は利用者が別の削除操作を行う |
| DL-08 | 取得失敗 | 失敗を表示し、利用者がURL・設定を変更して最初から再取得できる。アプリ側の自動再試行はしない。途中再開は必須にしないが禁止もしない |
| DL-09 | 変換失敗 | 取得済み動画を保持し、GUIから変換だけ再実行できる。再ダウンロードを必須にしない |
| DL-10 | 素材確認 | アプリ内の動画ビューワーと、フォルダ・ファイルのツリー構造から確認できる |
| DL-11 | 再利用 | 編集等で保存済みの素材を選んで使用する。再利用専用の別工程は要求しない |
| DL-12 | 元動画不在 | 実ファイルを必要とする操作で見つからなければ「元動画がありません」と表示する。情報・関連結果は削除しない |
| DL-13 | 中止・上書き・ログ | 第7章・第8章の共通仕様を適用する。入力・取得済みの正常な動画と新規未完成物を分ける |

**成功の範囲：** 取得完了、変換完了、ファイル保存完了、DB登録完了、再生可能であることは同一の事象ではない。対象操作が必要とする出力がそろっていることと、未完了の段階を区別する。具体的な登録順序・内部状態は未確定である。

**未確定の分岐：** URL1件から複数結果が得られる操作、動画を生成しない情報表示、音声だけの取得、任意パス・外部処理の指定について、通常の元動画登録とどう区別するかはJ-01で定義する。全CLI操作を勝手に削除せず、未解決の組合せを「すべて利用可能」とも扱わない。

### 4.2 F-02：文字起こし・内容と時刻の修正

| ID | 項目 | 動作仕様 |
| --- | --- | --- |
| AS-01 | 入力 | 元動画の音声を対象に文字起こしする。主な言語は日本語。対象の長さは1〜10時間を想定する |
| AS-02 | 出力 | 発話区間ごとに本文と開始時刻・終了時刻を含める。動画全体の先頭・末尾だけ、または処理日時だけでは代替しない |
| AS-03 | 時刻の意味 | 対象話者が話し始め、話が途切れるまでの区間を求める。ASRの出力単位がその境界に一致するとは技術確認できていないため、実現方法は未確定として管理する |
| AS-04 | 閲覧・修正 | アプリ内で本文のすべてと各区間の開始・終了時刻を修正できる。日本語に加え、人が英語を入力・表示できる。自動翻訳は必須にしない |
| AS-05 | 通常保存 | 本文・開始・終了の手修正をローカルDBへ自動保存する。通常時に利用者の保存操作を必須にしない |
| AS-06 | 保存済み内容 | 自動保存完了分を開き直して利用できる。保存前に終了した変更の自動復元は求めない |
| AS-07 | 保存失敗 | 失敗を表示し、アプリが動いている間は未保存の入力を保持する。利用者が保存を再試行し、アプリ側で失敗した保存を自動再試行しない |
| AS-08 | 再実行 | 正常に得られた新しい文字起こし結果は以前の結果と別々に保存する。以前の手修正済みデータを上書き・削除しない |
| AS-09 | 使用結果の選択 | 解析・トリミングに使用する文字起こし結果は利用者が選ぶ。最新の結果を自動選択しない |
| AS-10 | 手修正の履歴 | 再実行結果の別保存と、毎回の手修正の全履歴保存を区別する。後者は必須にしない |
| AS-11 | 前工程の変更 | 文字起こしを後から変更しても、既存の解析結果・クリップを自動再生成・削除しない。古くなったことを知らせる専用表示は設けない |
| AS-12 | 内容の品質 | 内容の正確さ・妥当性をアプリが自動で判断する機能は初回版に実装しない。利用者が閲覧・修正して判断する |
| AS-13 | 処理エラー | 文字起こしの失敗を表示し、該当処理だけを終了する。入力、保存済み結果、自動保存済み修正は保持し、利用者が再実行する |

**対象話者の条件：** 文字起こし対象は基本的に1人だが、動画内の話者が1人に限られる意味ではない。声が重なる場面でも対象者だけを扱いたいという希望と、個人の声のローカルモデルを用意できるなら利用したいという希望を保持する。初回版の必須範囲・採否・参照音声やモデルの方式は未確定である。

ASRモデルがローカルにあることを、個人の声を登録・学習できることの証拠にしない。話者ラベルが付くことも、重なった音声が分離されたことの証拠にはしない。

### 4.9 後続版・条件付き将来案の保持範囲

F-04では、利用者がGUIから動画を選び、投稿先アカウントを設定で管理し、YouTube Data APIで必要な入力情報と公開状態を扱うことを想定する。投稿した動画の情報・投稿内容、評価のために取得した情報をDBに保持する。投稿動画の削除だけで保存情報を削除せず、GUIから閲覧する。アップロードの失敗・成否不明時の具体動作は未確定である。

F-05では、チャンネル運用開始後、開発者の指示で評価・指標・期間・集計・報告の仕様を作る。評価結果・報告内容はローカルDBで管理し、GUIから閲覧し、利用者が削除する。指標・期間・取得情報・報告形式は未確定である。

「OpenAPI」という名称を使う将来構想には、文字起こし内容からの動画概要・ストーリー、コメントからの盛り上がり抽出、レビューがある。指すサービスの正式名称、利用API、コメント取得元、判断基準、レビュー対象は未確定であり、別サービス名へ自動置換しない。有料利用の承認条件は第8章に定める。

## 7. 失敗・中止・終了・復元・上書きの仕様

### 10.6 RI-03：対象話者・重なる声・ローカルモデル

#### 10.6.1 混同しない4つの処理

| 処理 | 欲しい出力 | 当時の要件との関係 |
| --- | --- | --- |
| 発話検出（VAD） | 人の発話がある時刻 | 「誰か」は分からない。 |

| 対象話者抽出（TSE） | 混合音声から、登録した対象者の音声 | 重なる声を含め対象者だけASRへ渡す候補。ただし抽出精度・欠落・漏れは別評価。 |

#### 10.6.2 候補比較

#### 10.6.3 本アプリに対する結論

**対象者の参照音声を使って重なる音声から抽出する公開実装は存在するため、「無料のローカル方式では原理的に実現できない」とは結論しません。** 一方、当時の候補で、日本語ゲーム実況等の対象者だけを必要な品質で漏れなく文字起こしできるという公開根拠までは得られませんでした。

WeSepではローカル設定・学習済みパラメーターと、混合音声・登録音声を使う経路が読めます。参照音声を渡すことは、利用者自身が毎回個人専用モデルを学習することとは別です。Hubの一部ソースにApache-2.0のヘッダーがあることから、**リポジトリ全体・配布重み・学習素材まで同じ許諾と推定しません**。[E20][E21]

**不足：** 候補モデル単位の利用許諾、対象言語・雑音・声質・非発話時の他者漏れ・時刻保持に対する裏付けです。初回版での必須性と採否はまだ利用者判断の対象です。話者分離を省いた方法を、同じ要求を満たす代替として勝手に採用していません。

本章の公開情報調査では解析プログラムも正解データも作成していません。具体例・誤り例・規則の範囲を整理した後に、残す処理と除外案の採否をまとめて判断する必要があります。通常のトリミングは、これらの解析が未確定でも独立する既定方針を維持します。


### 10.8 RI-05：発話・非発話区間のトリミング

本書内の関連仕様：TR-01〜TR-11、J-03。

| 実現したいこと | 公開機能・根拠 | 判定・条件 |
| --- | --- | --- |
| 人の発話区間を得る | Silero VADは発話時刻を秒／サンプル単位で返す。8kHz/16kHz対応。[E25] | **対応**。人物の識別や発話内容の正しさは提供しない。 |
| 音量が低い区間を得る | FFmpeg `silencedetect`は音量閾値と持続時間による検出。[E07] | **対応するが用途が違う**。人の非発話や対象者の非発話の判定とはしない。 |
| 対象者の発話区間を決める | ASR・VADだけには対象者指定がない。[E13][E25] | **条件付き／未確定**。RI-03の識別・抽出結果や修正情報との組合せが必要。 |
| 任意の開始・終了時刻で切る | FFmpeg `-ss/-t/-to`、`trim/atrim`。[E06][E07] | **条件付き**。codecコピーの切断位置と再エンコードの切断位置は同じ精度ではない。 |
| 本文・時刻の手修正を反映 | 切り出し側は時刻を入力として受け取れる。[E06] | **条件付き**。選択した保存結果から時刻を渡す処理はアプリ側。 |
| 前後余白を加えて端を収める | 入出力に開始・終了を指定できる。[E06] | **アプリ側の計算で構成可能**。余白値を加減し、元の時間範囲内へ収める。値・丸め規則は未決。 |
| 非発話区間も出力する | 切り出しは区間の意味によらず実行できる。[E06][E07] | **条件付き**。採用した発話区間の補集合を作るなどの方法は設計案。未知・認識失敗を自動で非発話にしない。 |
| 分割後も原動画の時刻と対応 | 時刻指定・タイムスタンプ調整手段がある。[E06][E07][E08] | **条件付き**。区間開始のオフセット、音声開始、フレーム／サンプル境界を保持する。 |

**切断精度の制約：** `-ss`で入力をシークすると、一般に直前のシーク可能点へ移動します。再エンコード時のaccurate seekとstream copyでは、そこから希望位置までのデータの扱いが異なります。`trim/atrim`自体もタイムスタンプのゼロ開始化とは別です。したがって、無再エンコードを常に選んで任意の発話境界どおりに切れるとは結論しません。[E06][E07]

**依存関係の重要点：** 音声が複数人の場合、「対象者の非発話」は「全員が黙っている」とは異なります。切り出す技術自体は成立しても、対象者の区間が決まらなければその意味での出力は確定しません。これはRI-03とRI-05をつなぐ未解決事項であり、無音除去へ置き換える根拠にはしません。

#### 10.9.3 動画の書き出しとプロジェクトの保存

出力SDKには、映像・音声を取得してファイルを作るための`OUTPUT_INFO`と`func_output`があります。これはホストから出力プラグインを呼ぶ契約であり、**本アプリから既存の出力処理を任意に開始・停止する一般APIを確認したことにはなりません**。[E32]

全シーンのレンダリングデータを使って別のエンコーダーへ渡す案は考えられますが、アプリ側の実装を要する構成案です。特定のMP4出力プラグイン、codec、オーディオ形式を正式に選定したわけではありません。

`PROJECT_FILE`の名前や保存イベントの存在だけで、現在の全プロジェクトを任意のパスへ保存・再読込する関数があると読み替えません。**外部からのプロジェクト保存・再開と、動画出力の起動経路は、当時読解したSDKだけでは一連の制御を確定できません**。[E31][E32]

**結論：主要な編集指示をプラグイン経由で扱う材料は確認できる一方、当時読解した範囲では、WSL側からそのまま使える完成した外部制御経路までは確認できませんでした。** 接続方式・保存起動・全操作対応を未確認のまま本書の確定した実行方式としないでください。


### 10.10 RI-07：処理中止と、処理開始直前への自動復元

本書内の関連仕様：第7.4節・第7.5節、J-04。

#### 10.10.1 何が確認でき、何ができないか

| 確認対象 | 公開情報・読解 | 判定 |
| --- | --- | --- |
| 編集をまとめて実行 | `call_edit_section`は更新ロック下でコールバックを呼び、変更したオブジェクトをまとめてUndoへ登録する。[E31] | **対応する基礎機能あり**。失敗時の自動ロールバック契約ではない。 |
| シーン設定の取り消し | シーン名・解像度・フレームレート・サンプルレートの操作に、Undo非対応の注記がある。[E31] | **通常Undoだけの方法では非対応部分あり**。全編集の完全復元へ一般化しない。 |
| プロジェクト全体のsnapshot | プラグイン領域の保存・ロード通知はある。[E31] | **判断不能**。以前の未保存手編集も含めた完全snapshot/restoreの一般入口は確認できない。 |
| 出力の中止状態を知る | `func_is_abort`はホストの中断状態を調べる関数。[E32] | **対応範囲限定**。外部アプリから中止を要求する関数ではない。 |

| 処理前の編集を守って自動復元 | 個別取得・変更の仕組みはあるが、全変更の網羅・逆操作・外部副作用の契約は揃わない。 | **判断不能**。仮実装せず、この不足を残す。 |

#### 10.10.2 採用済みの復元要件に対する判断

**「編集を一度Undoにまとめれば、どんな処理も完全自動復元できる」という案は、そのままでは成立を確認できません。** シーン操作の明示的な制約があり、別の時点の保存ファイルへ戻すだけでは、利用者の既存の未保存編集を失う可能性があります。

復元方式の候補として、変更前の値とオブジェクトの記録、対象限定の逆操作、処理単位の分離等は考えられます。しかしこれは**設計上の案**であり、全プラグイン・全効果・すべての状態を含む復元が可能とする証拠ではありません。APIの名前を並べただけで条件を満たしたとはしません。

**現時点で必要な扱い：** 自動復元要件は維持し、成立性の判断を保留します。通常Undoだけに依存する案を確定しないこと、完全復元を確約できる対象・状態・外部副作用の範囲を公開仕様で限定できるかを管理事項として残すことです。手動復元へ無断で要件を下げません。

#### 10.13.1 WSLとの組合せ

SQLiteのWALは、利用する全プロセスが同一ホスト上で共有メモリを使えること等を前提とし、ネットワークファイルシステム上では動かないと説明されています。[E42] **Windows側とWSL側から同じ稼働DBを同時に直接開いて安全、と推測しません。** 当時の別PC引き継ぎは同時共有ではないため、保存時点を切り分ける設計と区別できます。

#### 10.13.2 対象版で確認すべき修正情報

公式WAL文書にはWAL-reset問題の説明があり、3.51.3以降、および一部旧系列の修正版3.44.6・3.50.7で修正されたとされています。問題の条件は複数接続が書込・checkpointを近接して行う場合等です。[E42]

**採用条件への示唆：** WALを使う案では、実際にリンクされるSQLiteの版・修正状態を固定する必要があります。当時、利用者環境に問題があると判断したり、更新したり、故意に再現試験を行ったりはしていません。

**結論：DB引き継ぎの基本手段はありますが、移行形式・schema互換・既存DB保護・参照先変更・秘密情報除外を設計する必要があります。** GUIの作成・動作確認は実施していません。

| 新規の未完成ファイルだけを消す | ファイル操作やジョブの保存情報を使う構成は可能。 | **アプリ実装が必要**。ツール群に共通の「安全に消してよい」判定は存在するとは確認できない。 |
| 次回起動時に残骸を分類 | 保存された処理・生成物情報を参照する案は可能。 | **アプリ設計が必要**。単に一時フォルダにあるだけで削除しない。 |
| 新成果物完成後に置き換える | `os.replace`等の置換機能がある。[E49] | **条件付き**。成功時の原子的な置換と、同一ファイルシステム等の条件、許可・永続化は別。 |
| 失敗しても旧動画とDB両方を守る | DBトランザクションとファイル操作は別の仕組み。[E38][E49] | **全体としては未確定**。同じトランザクションに自動的に包まれない。 |
| 失敗後は手動再実行 | 呼出元が自動的に再投入しない構成は可能。 | **アプリの制御方針**。yt-dlp等の内部retry設定を一律無効化することとは別。 |

**設計案として残すこと：** 処理ごとの生成物台帳、入力・完成済み・未完成・復元用の分類、専用の出力領域、完了後の登録・置換、判別不能時は削除しない扱いです。これは当時新たに必須のDB列やフォルダ名を決めたものではありません。

**結論：安全な制御を作る材料はありますが、ツールの終了コードとファイル削除をつなげるだけでは要件を満たしません。** 任意の失敗でデータを失わないことを、公開APIの存在だけで保証しません。仮実装・故意の失敗試験は行っていません。
