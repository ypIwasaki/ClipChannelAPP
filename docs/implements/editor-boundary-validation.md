# 編集排他・保存から出力への移行・生成削除復元の検証

2026-09-18。利用者の追加検証依頼に基づく使い捨て試験。仕様確定・製品実装・Issue分割ではない。元仕様と素材は保持した。

## 判定

| 対象 | 実測 | 判定 |
|---|---|---|
| 編集適用中の手編集排他 | 20秒のSDK編集セクション前後で状態一致。境界付近のドラッグは未確定表示を残し、解除後のクリックで移動が確定 | 部分確認。入力を捨てる／明示的に待たせるUIまでの成立ではない |
| 保存から出力までの競合防止 | 保存済み状態は専用出力入口を通過。保存後の字幕変更ありでは出力拒否・成果物なし | 部分確認。保存通知と変更世代だけによる保証は不十分 |
| 生成・削除を含む一般的な復元 | 削除・再生成した字幕のgroupが消失。alias比較では同一と見えてしまう | **aliasだけの復元方式は不成立**。全方式の実現不能を意味しない |

`check-boundary.py`の12項目は、上記の反例を含む観測事実の照合に成功したもの。要件12項目の合格ではない。

## 構成

既存の隔離AviUtl2環境と同版SDKを使用。追加DLL `clipchannel_boundary_probe.aux2` はSHA256 `7F14731169E8AEC319A94B25DAEA1BC365BF8909DA8A0504A98DF85DE08A7009`。利用者が信頼確認を操作した後にロードした。ソースとビルド手順は `evidence/editor-sdk/boundary-probe.cpp` と `build-boundary.cmd`。

`boundary-fixture.aup2` は映像3・字幕3・画像1・補助音声1の検証コピー。第2映像と第2字幕がgroup=1。先頭字幕Y=60は前回の試験から保存済みであり、今回新たな先行未保存変更として扱わない。

## 生成・削除の復元

1. 第2字幕のaliasと位置を記録し、削除後、同一編集セクション内で同じaliasから再生成した。削除中は固定8個のsnapshot取得がINVALIDとなり、再生成後は元と同一になった。
2. 保存aup2の比較では、字幕の `group=1` だけが失われた。対応映像のgroupは残った。本文・効果・位置を含む他のオブジェクト情報は一致した。**alias一致だけでは復元成功を誤判定する反例**である。
3. ホストCtrl+Z一回で削除・再生成を取り消し、保存すると全8個のオブジェクト情報が元と一致した。これはホストUIのUndoによる復元で、自動復元用SDK入口や履歴競合の成立ではない。
4. 空きレイヤーに画像を1個生成し9個の保存状態を確認した。別の編集セクションでその画像を削除すると8個へ戻り、元の全オブジェクト情報を保持した。

SDKのdelete_objectには「同一編集セクション内で作成したオブジェクトは削除しないようにすること」とあるため、生成物の補償を同一セクションで実行する方式は使っていない。2セクション間の競合防止、履歴を1操作にまとめること、再起動後の復元、任意シーン／効果／外部プラグインデータの完全復元は未成立。今回の正常往復は追加の模擬失敗ケースとして数えず、既に実施した編集模擬失敗1件を再注入していない。

## 編集適用中の手編集排他

SDKのcall_edit_sectionはメインスレッドで更新ロックを保持する。変更せず20秒待つ試験で、保持前後の8個の取得状態は一致し、保持区間内のUPDATE_OBJECTは0件だった。

- 初回は20,031ms。ドラッグ要求は終了後に届いたため、保持中排他の実証に数えない。
- 2回目は20,032ms。ドラッグ要求の開始UTCとローカルtick対応から、要求開始は保持終了の約0.8秒前。正確なOS入力配送時刻は測定していないため、全入力が保持中に到達したとは断定しない。
- 解除後にドラッグの未確定表示が残り、Escapeでは表示が変わらず、後続クリックで移動が確定した。UPDATE_OBJECTは保持終了の46,297ms後。この移動はUndoで取り消した。

ロック内の取得状態が変わらないことと、待機入力が後で処理されることを区別する。長時間メインスレッドを止める方式を製品の操作待ちUIとして採用する根拠にはならない。モーダル処理・メッセージ処理を挟む実際の複合編集や、短い編集セクション間も含めた排他は別途成立が必要。

## 保存から出力への競合

専用出力プラグインは保存通知時の世代・識別値を保持し、出力コールバック入口で世代とディスク上の識別値を検査する。通過後は360フレームを読み、チェックサムを記載した `.ccprobe` ファイルを作る。これは完成動画エンコードではなく、ホストの実際の出力コールバックで判定ができるかの検証である。

正常状態では識別値 `18200-109458375-6` で成功し、360フレームの記録を生成した。その後、第3字幕Xを0→5へ変更し保存せず出力すると、`save marker absent on disk` で拒否し、指定した `boundary-dirty.ccprobe` は存在しなかった。

この間、明示保存していないのに識別値 `18200-109458375-7` の保存通知が届いた。同識別値を検証環境の `data/Backup/AutoBackup_2026-09-18_15-15-31-933.aup2` で確認した。バックアップにはX=5、明示保存先にはX=0と識別値6が残っていた。今回は識別値の照合が出力を止めたもので、変更世代の不一致による拒否を実証したとは扱わない。

最新の保存通知を「利用者の明示保存完了」と扱う方式は不可。保存要求と対象パスの対応、バックアップ通知の分離、保存済みの全状態との一致、通知遅延を含む開始境界の保護が必要。専用入口以外のホスト標準出力は、このプラグインのガード対象ではない。全入口の競合防止や出力開始までの原子的な移行は未成立。

## 後処理と証跡

試験の手変更をUndoで戻して保存。`boundary-final.aup2` の全8個のオブジェクト情報は初期コピーと一致（focusのみ比較除外）。ファイル全体のバイト一致は、保存識別値やカーソル位置が変わるため要求していない。

証跡は `evidence/editor-sdk/boundary-*.aup2`、`boundary.jsonl`、`boundary-clean.ccprobe`、`boundary-result.json`、比較スクリプト `check-boundary.py`。原仕様のSHA256は `CFC9E65594F7B72470DDDEF9EFA06776DA0FA28A2B884B57F6445082F8F83DC7`。

ADR-0003の「復元の成立根拠が揃わない操作は状態変更を止める」という条件は維持する。今回の不足を要件から削除せず、既存ゲートを完了扱いにしない。次の検討対象は、ホストUndoを安全に呼び戻す経路と、明示保存した状態を特定して出力する経路である。
